# 新增内容判据（Addition Criteria）

> 本文件是 career-copilot 的**常设演化判据**。任何对 `SKILL.md` / `references/` / `scripts/` 的改动，落地前都必须先过下面两道第一性原理 + 一道哲学合规门禁。
> 来源：`notes/audit-borrowing-plan.md` §0 判定框架；两个第一性原理取自 `references/evolution-log.md` 的 User Preferences。
> 本判据本身**不新增运行时负担**——它约束的是"我们改这个 skill 时的决策"，不是 skill 运行时的行为。

---

## 两道第一性原理（缺一不可）

每条新增/修改内容必须能回答：

- **(A) 是否提升判断质量或可靠性？**
  —— 它让输出更准、更少幻觉、更可验证吗？还是只是"听起来更专业"？
- **(B) 是否修复真实 / 高概率认知故障？**
  —— 它堵的是一个**真实发生过**或**高概率会发生**的错误模式，还是想象中的风险？
  - 判据：能否举出具体的失败案例 / 故障信号？举不出 → 多半是臆想风险，否决或降级。

**任一答不出 → 否决或降级为"可选 minor"。**

---

## 哲学合规门禁（撞一条即否决）

career-copilot 的设计哲学（详见 `SKILL.md` 与 `notes/archive/skill2.0-upgrade-plan.archived.md`）：

- 🚫 **不引入显式 `/命令`** —— 单 skill、靠理解意图路由是立身之本，硬命令会钝化最大优势。
- 🚫 **不拆多 skill** —— 软意图路由 + references 按需加载已覆盖拆分诉求。
- 🚫 **不钝化 AI 灵活性** —— 任何把"判断"降级为"查表/模式匹配"的机制都需警惕。
- 🚫 **不迁运行时** —— 不把工作逻辑搬出 `scripts/` 已有脚本。
- ✅ **红线用"负面 + 归因 + 豁免"结构** —— 已成熟，不因"Negation 反模式"批评就改写正面（见下"否决清单"）。
- ✅ **隐蔽的 fallback 比显式报错更危险** —— 任何降级 / 兜底 / 跳过必须显式标注。

## BOSS 直聘抓取判据（P6 留痕）

BOSS 直聘抓取是"借鉴"而非"核心能力"，按以下判据执行（满足 **(A)** 提升可靠性、**(B)** 堵真实风险——自动投递/静默编造是真实发生过的高危故障）：

- **只 fetch/score，send 归用户**：脚本只负责把 BOSS 岗位**拉取 + 结构化 + 评分**；**绝不自动投递、绝不代发消息、绝不点击申请**。发送动作永远停在用户手里（撞红线"不替代决策"）。
- **后端按实效选型，不预设硬依赖**：候选后端（bsk / 占位 stub）逐个实测，谁在当前环境真跑通就用谁；不把某一后端写死为唯一路径。
- **缺后端优雅降级**：当所有后端都不可用（未安装 / 登录失效 / 反爬拦截）时，`available()==False` 且 `search()` 抛 `BackendUnavailable`，由上层提示用户手动提供 JD，**不静默编造岗位**。
- **刹车兜底**：`search_jobs(max_jobs=)` 硬性截断返回条数，防止一次抓全城；`max_jobs=0` 才不限制。

> 留痕：BOSS 是"借鉴"边界案例——它扩了能力但引入反爬/账号风险，故采用"薄封装 + 可插拔后端 + 抓取/评分与发送分离"三原则，把风险关在最小面。任何对其行为的松弛（如默认开启自动投递）都需回到本判据复议。

## 使用方式

- 提改动前，在改动说明里显式标注它满足 **(A)/(B)** 哪条、是否撞哲学门禁。
- 评审他人改动时，先问"这堵的是真实故障还是想象风险"，再问"这钝化灵活性了吗"。
- 本文件与 `audit-borrowing-plan.md`、`notes/archive/skill2.0-upgrade-plan.archived.md` 互为补充：计划讲"这次改了什么"，本文件讲"以后怎么判"。
