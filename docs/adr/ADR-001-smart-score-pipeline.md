# ADR-001: smart_score.py 六阶段评分 Pipeline 架构

- 状态：已采纳
- 日期：2026-07-23
- 决策者：闫飞宇

## 背景

求职场景需要从数百个 JD 中筛选出与候选人最匹配的岗位，并输出结构化评分（A/B/C 三档 + risks + 迁移距离分析）。纯 LLM 方案存在两个核心问题：(1) 评分不可靠——同一 JD 多次调用分数漂移；(2) 硬约束（英语门槛、学历、技术栈）无法保证——LLM 可能忽略 JD 中的硬性要求。

## 决策

采用「模型判断 + 代码约束」的分层架构，将评分流程拆为六个阶段，每个阶段有明确的职责边界：

### 六阶段设计

| 阶段 | 职责 | 执行者 | 设计理由 |
|------|------|--------|----------|
| Pre-Filter | 确定性排除（实习/外包/年限/英语硬门槛/方向词） | 代码 | 100 个 case 答案都一样的判断，不浪费 LLM token |
| Stage 1 粗筛 | Pointwise 打分，全量 JD | 便宜模型 | 先粗后精，控制成本 |
| Stage 1.5 校准 | 生成辨别知识（易混淆岗位区分） | 强模型 | 注入行业知识，减少表面匹配误判 |
| Stage 2 精排 | Listwise 分组对比排序 | 强模型 | 对比排序强制拉开分差，比 Pointwise 更稳定 |
| Stage 2.5 全局重排 | 跨组全局排序 | 强模型 | 解决组间分数不可比问题 |
| Post-Judge | 确定性后处理（英语/核心团队/技术/A档分布） | 代码 | 硬约束 100% 由代码保证 |

### 关键设计取舍

**为什么 Listwise 而非 Pointwise？** Pointwise 独立打分导致分数聚集（大量 75-85），无法有效区分。Listwise 强制排序 + 分差约束（≥15 分）产生更有区分度的结果。

**为什么需要 Stage 2.5 全局重排？** Stage 2 按组排序，组间分数不可比（A 组第 1 名 95 分可能不如 B 组第 1 名 90 分）。全局重排用一次 LLM 调用解决跨组排序。

**为什么 Post-Judge 用代码而非 LLM？** 英语门槛、学历约束是二值判断（满足/不满足），LLM 有概率忽略。代码保证 100% 执行。

### 熔断器设计

Stage 1 使用 `processed_failure_rate`（已处理样本的失败率 = failed / (succeeded + failed)），而非 `failed / total`。原因：200 个 JD 中前 25 个全部失败时，`25/200 = 12.5%` 低于 30% 阈值不会触发熔断，但实际失败率是 100%。用已处理样本的失败率能在小批量失败时及时中止。

### 配置外部化

关键确定性约束（A 档比例 `a_tier_cap`、Post-Judge 生效判定 `post_judge_check`）集中在 `config/constraints.yaml` 作为单一事实源（改约束只动这一处，避免代码/文档/测试三处同源漂移）；其余数值参数（模型、并发数、分数带、熔断阈值、后处理惩罚）集中在 `config/pipeline.yaml`，prompt 模板在 `config/prompts.yaml`。代码内有完整默认值兜底（`load_config()` / `load_constraints()`），YAML 缺失时零回归。分数带参数通过 `{placeholder}` 注入 prompt 模板，改配置不需要改代码或 prompt 文本。

## 后果

- 正面：评分结果可复现、硬约束有保证、成本可控（便宜模型处理 80% 工作量）
- 正面：配置外部化后调参不需要改代码，prompt 和数值参数分离管理
- 负面：完整 Pipeline 需要多次 LLM 调用，200 个 JD 预计 5-10 分钟
- 负面：六阶段增加了代码复杂度，需要 200 个测试保证不回归
- 风险：Golden Cases 仅 1 个人工标注，评分准确度尚未充分验证
